# 四玩家区块加载优化验收（2026-09-29）

最终实验构建：`build/libs/muxi-game-core-1.10.0-dev.jar`，SHA-256：
`b378c36403c6d8e75cb3d07f3d1ca0b25307a6c780b7db9b886242377afcd8ed`。

本轮把玩家/载具移动包的冷区块读取改为非阻塞准入，加入近处优先预加载、请求预算、生成并发上限和限速预生成。具体行为与命令见 [功能说明](chunk-travel.md)。实验线程总开关仍默认关闭，未安装到正式服务器。

## 结果

四个原生客户端同时在两个维度、四条互不重合的路线移动。每种配置只测一次，不能把微小差异解释为稳定加速比例。

| --- | ---: | ---: | ---: |
| 平均 TPS | 10.93 | 20.00 | 20.00 |
| 最低 20 tick 窗口 TPS | 0.51 | 15.31 | 17.50 |
| 四人首次全部确认到达 384 格终点 | 45.16 s | 61.94 s | 43.86 s |

| 服务端平均 CPU 核心当量 | 1.31 | 1.30 | 1.61 |
| 四客户端平均 CPU 核心当量 | 4.54 | 4.69 | 4.80 |
| 整机平均 CPU | 95.12% | 97.61% | 97.24% |

最终版明显减少了全服 tick 停顿，没有重现第一版额外引入的路线耗时。43.86 s 与基线 45.16 s 接近，本轮不足以证明跑图吞吐普遍更快。平均 CPU 占用有所提高；固定路线对应的采样累计 CPU 时间接近基线，也不能据此承诺节省 CPU。

机器阶段三组均约 20 TPS，平均 tick 工作耗时分别为 3.40、3.19、4.90 ms。本轮没有证明机器阶段耗时改善。原生客户端同机运行，CPU 接近饱和，这些数字不是专用服务器的容量上限。

![TPS 与位置采样](../build/chunk-travel-ab-20260929-105347/travel-comparison.png)

TPS 使用实际 tick 间隔计算，最低值采用滚动 20 tick 窗口，展示上限为 20。tick 工作耗时不包含两个 tick 事件之间的全部区块任务。位置图每 20 tick 采样一次，阶梯线保留上一次观测；长平台表示没有更新的采样，不能据此断言玩家在整个区间完全不动。到达时间在每个服务端 tick 末检查，不能代替逐帧的玩家感知延迟。

## 实测发现并修复的问题

第一版准备好的预测区块在 20 tick 后就释放，即使它仍在玩家前方。玩家尚未到达便丢失票据，造成重复请求；票据额度紧张时，已完成的预测还会阻挡紧急请求。

最终版对仍在当前预测路径上的区块续期，离开路径后才进入释放宽限期；紧急移动可让已完成的非紧急票据腾出额度，保留原版玩家票据。整场测试中票据提交由 974 次减少到 282 次，移动等待计数由 981 次减少到 675 次。等待计数是请求次数，不是等待秒数，也不是独立卡顿次数。最终临时票据归零，峰值 48，符合上限。

两版实验仍可能让个别玩家在区块边缘短暂等待；目标是避免该等待同步拖住整个服务器，而不是允许玩家穿过未知地形。

## JFR 核对

探索阶段服务端主线程的执行/原生采样中：

| 含指定调用路径的样本数 | 基线 | 第一版 | 最终版 |
| --- | ---: | ---: | ---: |
| 玩家移动 → `ServerChunkCache.getChunk` | 76 | 0 | 0 |
| 任意 `ServerChunkCache.getChunk` | 77 | 5 | 11 |
| `postProcessGeneration` → `getChunk` | 42 | 5 | 11 |

计数重叠、测量时长不同，不能换算为 CPU 百分比或精确阻塞时间。未采到某条路径不证明它永远不存在。结果支持移动准入避免了这条主线程等待路径；FULL 激活/流体后处理仍可能同步取块，GC、模组任意同步读取、实体自主运动和全局屏障也仍有影响。

## 方法与通过项

- Ryzen 7 9800X3D，系统报告 8 个逻辑处理器，Java 21.0.2。服务端 G1、Xms 8 GiB / Xmx 20 GiB、`ActiveProcessorCount=4`；每个客户端 G1、最大 8 GiB、处理器提示 1、隐藏窗口、10 FPS。处理器提示不是 CPU 亲和性或硬配额。
- 338 个服务端 JAR、每客户端 416 个 JAR。C2ME 排除在隔离测试实例之外，Spark 后台采样关闭。三个实例除 core 构建外，其余服务端模组字节相同，测试夹具按解压内容相同。
- 两位玩家在家园、两位在生存，同维度玩家相隔 2048 格。全新世界，种子 12345；视距与模拟距离均为 3。先准备远处出生点，四客户端完成启动后顺序入服，全部就绪后预热 600 tick。
- 机器测量 400 tick，然后四人同时走固定 384 格。探索至少测量 600 tick，未完成就继续，最多 2400 tick，全部到达才进入传送验收。基线和最终版测量时长因此不同，保留完整路线时间与位置轨迹。
- 128 台熔炉、128 个漏斗与箱子、256 根 Create 转轴持续工作，机器所在区块强制加载。自然刷怪关闭，不代表 Boss 战或所有实体负载。
- 三组均通过 16 项服务端功能检查：路线与分散位置、熔炉产物、漏斗转运、Create 转速。12 次原生客户端运行全部成功，物品数量 23、等级 7、跨维度同步、断线重连与截图完成；服务端均退出 0，并通过存档重启恢复。
- 三组客户端当前所在区块缺失采样均为 0。此检查不表示周围全部区块可见，也不代表 GPU 已完成地形渲染。
- 最终构建另通过 21 项专项回归，覆盖冷区块玩家/载具移动包、位置纠正、就绪后准入、急转弯、超大位移边界、九区块预生成、取消和票据释放。冷玩家请求约 3.52 ms 返回，目标区块当时仍未生成。该夹具在触发 `ServerStopped` 后仍有后台线程，测试脚本按既有清理策略结束进程；这与四原生客户端的正常退出记录分开报告。
- 既有构建自测 6910 项通过，不把它们算作新增并发测试。专项夹具曾漏掉上船后的传送确认包，补全协议后重新通过；失败记录未混入性能结果。

基线与第一版均为 `6d550092ab80bfc378d6328807f66c992275835d15ab03b6e07d5de6545400ea`，只切换 `muxi.chunkTravel.disabled`。最终修正版为上方 `b378...` 构建；逐 JAR 条目核对，只有 `ChunkTravel` 及其内部类变化，其他 core 类和资源相同。基线关闭该服务，其代码路径未改；最终版是针对保留策略的后续复测，不冒充与前两组完全相同的二进制。

三组均启用维度并行与生成并发上限；本表隔离比较的是 travel 服务与保留策略，不是重新比较串行/并行架构，也不是独立测量生成信号量的加速效果。较早的架构/GC 比较见 [多人 GC 基准](multiplayer-gc-benchmark.md)。
