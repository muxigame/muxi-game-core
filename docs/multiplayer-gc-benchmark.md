# 四名原生玩家：维度并行与 GC 对照

2026-09-29 已完成四组、每组四名原生客户端的端到端测量和存档重启验收。功能检查全部通过，**四人跑图没有维持稳定 20 TPS，不能宣称独立加载线程使跑图不影响 TPS**。所有服务端仅监听一次性目录中的随机 `127.0.0.1` 端口，没有启动正式服或信令接入服务，也没有修改正式服的 JVM 参数、模组或存档。

## 结果与建议

四组使用同一核心 `1.10.0-dev`，SHA-256 为 `57c173a6199a2b786dfa8a00b124771b760e7677a9fe0e534787095154aad27a`。每组服务端 338 个 JAR，客户端各 416 个 JAR；四组服务端模组内容一致。测试夹具 JAR 在比较时对解压内容计算哈希，排除 ZIP 时间戳差异。

ZGC 两组在测量阶段均没有记录到分配等待。GC 相关安全点包含等待线程到达安全点的时间；例如并行 ZGC 的最长 GC 安全点 60.774 ms 中，60.384 ms 是到达安全点的等待。因此不能用 0.0163 ms 宣称所有业务线程最多只停顿这么久。全部安全点还包含 JVM 的 Cleanup 等操作。

机器阶段四组平均都约 20 TPS。G1 的平均 tick 工作耗时从串行 5.055 ms 降至并行 3.286 ms，减少约 35.0%；ZGC 从 3.887 ms 降至 3.382 ms，减少约 13.0%。这是墙钟耗时改善，不等于总 CPU 计算量同比下降。

跑图时，G1 下并行平均 TPS 比串行低约 3.5%，ZGC 下并行比串行高约 14.9%；趋势不一致，不能据此宣称普遍加速。并行架构内换用 ZGC，本轮平均 TPS 从 13.172 提高到 14.833，最长 GC 相关安全点从 146.107 ms 降至 60.774 ms，但服务端 CPU 从 1.676 核当量提高到 1.786，驻留内存从 9.494 GiB 提高到 21.544 GiB。串行架构内换用 ZGC，本轮平均 TPS 则没有提高。

**建议：正式服当前保留 G1；下一轮并行架构调试可优先使用 Java 21 分代 ZGC 作为低暂停候选。** 这不是正式切换建议：只有一轮对照，同机四端令整机 CPU 接近满载，尚不足以认定某组合在独立正式服务器上有稳定吞吐优势。并行开关继续保持实验性质，默认关闭。

当前优先需要优化的是主线程同步区块等待。最终 JFR 的主线程栈包含 `handleMovePlayer -> Entity.move/碰撞 -> ServerChunkCache.getChunk -> managedBlock`，区块激活后的 `postProcessGeneration` 和流体更新也出现在记录中；噪声、群系等生成计算确实在对应维度加载线程执行。tick 之间的这些任务与同机 CPU 争用仍会拉长实际间隔，解释了平均 tick 工作未超过 50 ms 却仍明显掉 TPS 的现象。执行采样只用于定位路径，不作为各路径 CPU 时间占比的精确统计。

## 对照设计

- 同一个 `1.10.0-dev` 核心 JAR，开关 `muxi.dimensionThreads` 关闭/开启，分别搭配 G1 与分代 ZGC，构成四组。每组使用新建的种子 12345 世界，依次执行，不同时运行两个被测服务端。
- 本机 Ryzen 7 9800X3D，系统可见 8 个逻辑处理器，约 189 GiB 内存。JDK 为本机 OpenJDK 21.0.2。服务端 `-Xms8G -Xmx20G -XX:ActiveProcessorCount=4`；四个原生客户端分别 `-Xms512M -Xmx8G -XX:ActiveProcessorCount=1 -XX:+UseG1GC`，隐藏窗口，限制为 10 FPS。
- `ActiveProcessorCount` 是 JVM 处理器数量提示，**不是 CPU 亲和性或核心配额**。客户端、服务端和其他桌面应用仍会争用同机 CPU，因此这是同机端到端负载对照，不能直接外推独立服务器的最大在线人数。
- 家园和生存各两名玩家，同一维度内两条路线相距 2048 格；每人飞行固定 384 格，以正常客户端移动网络包进入新区域。固定远端出生点在连接前准备了 3×3 个 FULL 区块，避免冷启动传送阻塞其他人的握手。本次不测冷出生点的同时入服容量。
- 四端先完成标题界面资源加载，再依次连接；重连检查也依次进行。四人全部就绪之后才预热和同时测量。初始实验在 Spark 后台采样开启时曾出现同机四端冷加载、同时登录的配置/协议切换超时，已保留失败证据；没有单独验证关闭后台采样能否解决同时冷登录。依次入服是本基准控制准备阶段的方法，不是宣称同时登录兼容性已通过。
- 全包服务端/客户端均去掉测试目录里的 C2ME，隔离核心身份/网络接入包，沿用测试脚本的公开配置白名单。这是“原生串行与自研并行”的比较，**不是 C2ME 对比**。G1 使用默认收集器参数，没有复制正式服原有的手工 G1 调优组合。
- 实验服务端明确设置 `config/spark/config.json` 的 `backgroundProfiler:false`，与正式服已有设置一致；只使用 JFR 采样。初始实验漏带该设置，Spark 在 Windows 上回退至 Java 引擎，约每秒请求 100 次 ThreadDump 安全点。那些数据被排除在最终排名之外，未据此修改正式服配置。
- 合计 128 台熔炉、128 个漏斗和箱子、16 台 Create 创造马达、256 根 Create 轴；两世界的机器区持续加载。四端全部进入游戏后预热 600 tick，然后测量机器阶段 400 tick、跑图阶段 600 tick。自然刷怪关闭，不能据此评估实体战斗和 Boss 压力。
- 每组继续执行跨维度、主动断线重连、钻石数量/经验/目的维度检查，并停服重启，核对全部熔炉和箱子的产出恢复。只有这些检查和进程退出均通过，才算该组成功。

## 指标定义

- 平均 TPS：相邻服务器 tick 开始时间的平均间隔换算，上限 20；短时最低 TPS 使用连续 20 tick 的滑动窗口。间隔包含两次 tick 之间的排队/区块任务等影响。
- tick 耗时：`ServerTickEvent.Pre` 到 `Post` 的墙钟时间，记录平均、P95、P99、最大值以及超过 50/100 ms 的数量。它不包含所有 tick 之间的工作，不能只用这个值解释完整 TPS。
- 跑图断言检查服务器收到的玩家最终坐标和分散路线；本测试没有测量“每个区块请求到客户端可见”的端到端延迟，也未以所有后台区块队列排空作为测量结束条件。因此较高 TPS 不能单独证明区块交付更快。
- CPU：每秒采样进程 CPU，100% 表示占满一个逻辑处理器；阶段结果以时间加权平均“核心当量”表示。分别记录服务端、四个客户端进程树、整机 CPU，阶段切换时混合采样区间不进入均值。
- 内存：进程 RSS/Windows working set，包含堆外和原生内存，不等于 Java 堆使用量；另记录 JFR 在 GC 时观测到的堆峰值。
- GC：两种收集器均打开 JFR profile 和统一 GC 日志；按测量阶段统计 `jdk.GCPhasePause` 暂停，以及 `jdk.ZAllocationStall` 分配等待。暂停阈值为 0 ms。一次并发回收周期的耗时不等于业务停顿时间。
- 同时解析 GC 日志的安全点总耗时，包含到达安全点的等待、清理和安全点内部执行，并分别记录全部安全点与 GC 相关安全点。`GCPhasePause` 很短并不表示所有线程停顿都同样短；CPU 争用等因素可能拖长到达安全点的时间。

这是一轮固定场景的四组对照，非多次重复的统计置信结论，也不是长时间稳定性认证。每次重启的 JIT、操作系统缓存、客户端渲染、区块调度和同机后台负载都可能带来变动。最终测试顺序为并行 ZGC、串行 G1、串行 ZGC、并行 G1，交替收集器，并先确认实际发现的并发故障已修复。

## 本次修复与被排除的实验

- 四名玩家分散到远端区域时，Sable 2.0.5 的全局方块碰撞缓存出现并发扩容越界，原始崩溃保存在 `build/thread-load-20260929-003145-228882`。最终补丁保护两份引用键布尔映射的每次访问，保留原有键和值语义，形状计算留在锁外。定向回归检查真实转换后的目标类，覆盖 468 种方块状态、两种判定、4 线程重复并发访问；并行两组及重启阶段均通过。
- 初始实验没有带入正式服已有的 `backgroundProfiler:false`，Spark 在 Windows 上使用 Java 采样引擎，产生约 100 次/秒的 ThreadDump 安全点。`build/thread-load-20260929-005117-881090` 中跑图阶段共 4966 次安全点，总耗时约 6.397 秒，不能与最终关闭该采样器的组混合排名。最终并行 ZGC 组为 45 次安全点，总耗时约 0.460 秒；这里只说明仪器配置问题，不将两次单轮运行的 TPS 差值当成普遍优化比例。
- 初始同时冷登录的配置超时、诊断夹具加载失败和端口占用记录均未进入最终结果。实验启动器改用动态客户端端口范围之外的空闲回环端口；最终采用依次入服。并未更改正式服登录超时或网络配置。
- 最终核心构建的既有 Java 自测 6910 项通过；新的并发缓存回归在真实整包服务端执行。Python 脚本编译检查与 `git diff --check` 通过。既有自测数不代表 6910 项新的并发覆盖。

## GC 选择依据

ZGC 已从 JDK 15 起成为生产级收集器，JDK 21 的分代模式使用 `-XX:+UseZGC -XX:+ZGenerational`。其目标是缩短暂停，大部分回收工作与程序并发；这不意味着回收没有 CPU 成本，也不保证内存分配总能赶上回收。堆空间或 CPU 余量不足时仍可能出现分配等待。[OpenJDK 官方分代 ZGC 说明](https://inside.java/2023/11/28/gen-zgc-explainer/)

更换收集器时应移除 `UseG1GC` 及 G1 专用调优项，不能与 ZGC 开关叠加。本机 21.0.2 属较早维护版本；正式采用前应在整包支持的 Java 21 范围内更新维护版本并复测。当前报告只评价本机实际运行的版本，没有修改正式配置。
